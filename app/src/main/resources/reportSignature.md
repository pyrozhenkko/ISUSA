# Технічний Звіт: Реалізація Асиметричного Цифрового Підпису

## Модуль забезпечення цілісності та неможливості відмови від авторства

**Тема:** Цифровий підпис для верифікації студентських заявок  
**Підсистема:** Security Subsystem (Підсистема безпеки)  
**Використані алгоритми:** RSA (2048 біт) + SHA-256 + Nonce

---

## Мета 

Заміна традиційного паперового підпису студента на внутрішній криптографічно стійкий цифровий підпис, який:

- не залежить від зовнішніх ЦСК (наприклад, «Дія»);
- забезпечує повноцінні гарантії автентичності, цілісності та неможливості відмови всередині університетської інформаційної системи.

---

## Гарантовані криптографічні властивості

| Властивість | Як забезпечується |
|-------------|-------------------|
| **Автентичність волевиявлення** | Повторне введення пароля студента при подачі заявки (перевірка через AuthenticationManager) |
| **Цілісність даних** | Зберігання SHA-256 хешу вмісту заявки + Перевірка RSA-підпису "відбитку" даних |
| **Неможливість відмови** | Підпис створюється серверним приватним RSA-ключем, який ніколи не залишає сервер |

---

## Архітектурні компоненти

| Компонент | Опис | Роль у системі |
|-----------|------|----------------|
| **Пароль студента** | Облікові дані користувача | Акт волевиявлення |
| **Хеш вмісту (ContentHash)** | SHA-256(application.content) | Відбиток тексту заявки |
| **DataToSign (Відбиток)** | (Виправлено) `studentId=...&applicationId=...&contentHash=...&timestamp=...&nonce=...` | Унікальний «відбиток» у форматі key=value, що підписується |
| **Приватний ключ (RSA)** | Секретний ключ сервера (зберігається лише в application.properties → пам'ять) | Генерація підпису |
| **Публічний ключ (RSA)** | Відкритий ключ сервера | Верифікація підпису |
| **Підпис (Signature)** | RSA_SHA256(dataToSign, PrivateKey) | Криптографічна «печатка», зберігається в БД |

---

## Процес підписання (Signing)

Виконується в `ApplicationService.signAndSubmitApplication`:

1. Студент надсилає заявку + свій пароль → `AuthenticationManager` перевіряє пароль.
2. Створюється запис `Application` в БД (отримуємо `applicationId`).
3. Обчислюється `contentHash = SHA-256(content)`.
4. Формується унікальний `dataToSign` (з `contentHash`, `applicationId`, `studentId`, `timestamp` та `nonce`).
5. Підписується приватним ключем: `signature = RSA_SIGN(dataToSign, PrivateKey)` (через `SignatureService.sign`).
6. Зберігаються поля: `contentHash`, `dataToSign`, `signature` в `Application`.

---

## Процес верифікації (Verification)

Виконується в `VerificationService.verifyApplicationIntegrity`:

### Аудит 1 – Цілісність вмісту (Чи не змінили текст?)

Сервер "перераховує" хеш поточного тексту:

```java
String currentHash = signatureService.hashData(application.getContent());
```

Порівнює: `if (!currentHash.equals(application.getContentHash()))` → **ПЕРЕВІРКА ПРОВАЛЕНА** (вміст змінено).

Якщо OK → Перехід до Аудиту 2.

### Аудит 2 – Автентичність Підпису (Чи не змінили "відбиток"?)

Сервер викликає:

```java
boolean isValid = signatureService.verify(
    application.getDataToSign(), 
    application.getSignature()
);
```

Метод використовує Публічний Ключ (`keyService.getPublicKey()`) для перевірки, чи `signature` дійсно є підписом для `dataToSign`.

- Якщо `isValid == false` → **ПЕРЕВІРКА ПРОВАЛЕНА** (метадані або сам підпис були підроблені).
- Якщо `true` → **УСПІХ**.

---

## Висновок

Тільки якщо обидва аудити пройшли, система підтверджує, що заявка є автентичною.
